# Пользовательские сценарии под e2e

Что проверяем в реальном браузере против собранного фронта и настоящего бэкенда.
Список закрывает пункты, по которым проект проверяют, плюс места, где юнит-тесты
бессильны по устройству — они проверяют слои по отдельности, а ломается стык.

## 1. Путь записи проходит целиком

Гость открывает список видов встреч → выбирает формат → видит календарь со свободным
временем → выбирает слот → заполняет имя и email → получает подтверждение с датой,
временем и названием встречи.

**Почему в e2e:** это главный критерий проверки проекта («путь записи проходит от выбора
слота до подтверждения»). Ни тест API, ни тест компонента его целиком не покрывают.

## 2. Созданная запись видна владельцу

После записи гостя владелец открывает свой список и видит встречу: время, название типа,
имя и email гостя.

**Почему в e2e:** проверка требует, чтобы запись «сохранялась и отображалась в интерфейсе».
Это единственный сценарий, который проходит через оба контура — публичный и админский.

## 3. Занятый слот исчезает из списка свободных

После записи то же время больше не предлагается другим гостям.

## 4. Занятость глобальная — между разными типами встреч

Часовая консультация, забронированная на 12:00, закрывает получасовое демо и на 12:00,
и на 12:30, но не трогает 11:30 (эта встреча заканчивается ровно в 12:00).

**Почему в e2e:** правило контракта, которое легко сломать оптимизацией запроса
(«брать брони только этого типа встречи») — и юнит-тест сервиса такую правку переживёт,
если заглушку поправят заодно.

## 5. Повторная запись на занятый слот не проходит, гость видит понятное сообщение

Слот занимают в обход браузера, пока гость заполняет форму. При отправке гость получает
сообщение о конфликте, а список слотов обновляется.

**Почему в e2e — и почему это главный сценарий списка:** 19.08 этот случай сломался ровно
здесь. Сервер отвечал `409` правильно, юнит-тест на API был зелёный, но сообщение на фронте
отрисовывалось внутри формы, которая на конфликте исчезала, — гость видел пустую панель.
Тест API поймать это не мог в принципе. Проверка проекта требует именно «понятное
сообщение о конфликте».

## 6. Владелец публикует тип встречи, и гость сразу его видит

Владелец заполняет форму в своём кабинете, тип встречи появляется в его списке
и на публичной странице.

## Чего в e2e осознанно нет

- **Валидация полей по отдельности** (пустое имя, email без собаки, время мимо сетки) —
  55 юнит-тестов покрывают это быстрее и подробнее. В браузере проверяется стык, а не
  комбинаторика входов.
- **Ветка Postgres.** Прогон идёт без `DATABASE_URL`, то есть на хранилище в памяти —
  ровно как проверка проекта. SQL по-прежнему не исполнялся ни разу.
