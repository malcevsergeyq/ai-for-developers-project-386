# Слой данных «Календаря звонков»

## Сначала — проверь, есть ли база

Не полагайся на утверждение в документации о том, накачена схема или нет: это самый быстро
протухающий факт в проекте. Проверяй исполнением:

```
psql --version          # есть ли клиент вообще
echo $env:DATABASE_URL  # задана ли строка подключения
docker ps               # поднят ли контейнер
```

По состоянию на 2026-08-09 все три проверки давали отрицательный результат: Postgres не установлен,
`DATABASE_URL` не задан, демон Docker не запущен. Если твои проверки показывают то же — **все тесты
идут на заглушках репозиториев**, и они подтверждают форму ответа, но не корректность SQL.
Пиши SQL с этой оговоркой и называй её в отчёте поимённо: какие конструкции остались непроверенными
(`ANY($1::int[])`, `FOR UPDATE`, транзакции, коды ошибок).

## Модель данных

Четыре таблицы, `server/schema.sql` — единственный источник истины по схеме.

```
availability_schedules ──< schedule_rules
        │
        └──< event_types ──< bookings
```

- **`availability_schedules`** — именованное расписание доступности с таймзоной.
  Таймзона берётся отсюда и только отсюда: сервер не использует свою локальную зону
  и не принимает offset от клиента.
- **`schedule_rules`** — интервалы по дням недели (`weekday` 1–7, `start_time < end_time`).
  Отдельная таблица, а не `jsonb`: нужны обычные сравнения и индексы по времени.
  Удаляется каскадом вместе с расписанием.
- **`event_types`** — тип события: `slug` уникален, `duration_minutes > 0`,
  `hidden` — фильтр публичности (не удаление).
- **`bookings`** — бронь: `token` уникален, `status` ограничен
  `('pending','confirmed','cancelled','completed')`, `created_at` проставляет БД.

## Что держит схема, а что код

Ключевое правило слоя: **инвариант, который уже держит база, не дублируется проверкой в коде.**
Код обрабатывает ошибку БД, а не предугадывает её. Дублирующая проверка расходится с ограничением
на первой же правке и даёт две разные истины.

| Инвариант | Чем держится | Что делает код |
|---|---|---|
| Один активный слот не занят дважды | `bookings_active_slot_uniq` — партиальный `UNIQUE` по `(event_type_id, date, start_time) WHERE status IN ('pending','confirmed')` | ловит `23505` → `409` |
| Нельзя удалить тип события / расписание со связанными записями | `REFERENCES` **без** `ON DELETE CASCADE` | ловит `23503` → `409` |
| `weekday` 1–7, `start_time < end_time`, `duration_minutes > 0`, допустимые статусы | `CHECK` | валидирует вход на границе (`routes`) → `400` |
| Отмена освобождает слот | партиальный индекс не покрывает `cancelled` | меняет `status`, ничего не удаляет |

Отсюда же способ создания брони: **не** «`SELECT` занятости → потом `INSERT`». Между двумя запросами
есть окно, в которое проедет вторая бронь. Правильный путь — сразу `INSERT` и разбор ошибки
уникальности. Это тот же урок, что в барбершопе: там защита от накладок держалась на побочном
эффекте однопоточности Node, и это было хрупко.

Оговорка про пересечение интервалов: партиальный индекс ловит **совпадение времени начала**,
а не пересечение слотов разной длительности. Пересечение проверяется в `services/intervals.js`,
и обе стороны — генерация свободных слотов и валидация при создании брони — обязаны звать
**одну** функцию.

## Коды ошибок Postgres → ответы контракта

| SQLSTATE | Что случилось | Ответ |
|---|---|---|
| `23505` | нарушение `UNIQUE` (занятый слот, дубль `slug`) | `409` |
| `23503` | нарушение `FOREIGN KEY` (нет такого типа события / есть связанные записи) | `404` при ссылке на несуществующее, `409` при удалении со связями |
| `23514` | нарушение `CHECK` | `400` — но чаще признак того, что валидация на границе не отработала |

Формат ответа всегда `{ error: "machine_code", message: "русское описание" }`.
Код ошибки Postgres наружу не протекает.

## Типы на границе БД и DTO

Драйвер `pg` возвращает не то, что ждёт контракт. Преобразование живёт **только** в `mappers/`:

- `date` → приходит объектом `Date`, отдаётся строкой `YYYY-MM-DD`.
  Форматировать через локальную зону нельзя — получишь сдвиг на сутки.
- `time` → приходит строкой `HH:MM:SS`, контракт отдаёт `HH:MM`.
- `snake_case` в БД ↔ `camelCase` в API.

Разъехавшийся маппинг даёт молчаливые `undefined` в ответе вместо ошибки — поэтому мапперы
тестируются отдельным файлом, а не только через HTTP.

## Миграции

**Механизма миграций нет, и решение о нём не принято.** Пока база не накатана, `schema.sql`
правится свободно. Как только база появится, правка схемы перестаёт быть самодостаточной.

Правило на сейчас: любое изменение `schema.sql` сопровождай **готовым `ALTER TABLE`**
и выноси его в отчёт отдельным пунктом. Накопленные с 2026-08-03 правки перечислены
в разделе «Открытые вопросы» `PLAN.md` — сверяйся с ним, а не с памятью.

DDL из кода приложения не выполняется никогда: ни `CREATE TABLE` при старте, ни «создам таблицу,
если её нет». Схему накатывает человек.

## Когда будешь поднимать базу

Не выполняй за человека — предложи и покажи команды. Требования к настройке:

- Postgres в Docker, чтобы не тащить службу в систему.
- **Две роли, а не одна.** Владелец схемы делает DDL; приложение ходит под ролью, у которой
  прав на DDL нет — только `SELECT/INSERT/UPDATE/DELETE`. Тогда «агент случайно уронил таблицу»
  становится невозможным физически, а не запрещённым на словах. Это граница последствий,
  а не фильтр намерений.
- `DATABASE_URL` — только в `.env` (он в `.gitignore`), никогда в коде и не в `AGENTS.md`.
- Строка подключения рантайма содержит роль без DDL.

## Тесты слоя данных

Пока живой базы нет, тесты идут на заглушках из `server/tests/helpers/`.
Требование к заглушке одно: **она повторяет семантику SQL, а не удобную для теста логику.**
Если запрос фильтрует `WHERE hidden = false`, заглушка фильтрует так же. Заглушка, которая
ведёт себя иначе, чем запрос, проверяет не то поведение, которое поедет в прод, — и зелёный
прогон в этом случае означает ровно ничего.
