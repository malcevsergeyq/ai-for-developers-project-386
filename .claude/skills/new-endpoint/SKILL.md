# Новый эндпоинт «Календаря звонков»

## Зачем нужен фиксированный порядок

`spec/main.tsp` — источник истины для фронта и бэка. Фронт пишется по нему, не заглядывая
в код сервера. Если реализация уходит вперёд контракта, контракт начинает врать, и ошибка
всплывает не здесь, а на стороне фронта, где её дороже искать.

Отсюда порядок: **контракт → схема → реализация → тесты**. Каждый шаг опирается на
зафиксированный предыдущий, а не на догадку о нём.

## Шаг 1. Сверить контракт

Прочитай `spec/main.tsp` и найди нужную операцию в интерфейсах (`PublicEventTypes`, `PublicBookings`, `AdminEventTypes`, `AdminBookings`).

- **Эндпоинт есть, поведение совпадает с задачей** → ничего не меняешь, идёшь дальше.
- **Эндпоинта нет, либо задача меняет его поведение** (другой код ответа, новое поле в DTO,
  другая семантика) → **сначала правишь контракт**, потом код.
- **Контракт молчит о случае, который встретился при реализации** (не описано тело успешного
  ответа, не определено поведение при пустом параметре, не сказано, что делать со статусом
  `completed`) — это нормальная и частая ситуация. Дополни контракт, но помни: ты принимаешь
  решение за человека, поэтому оно должно быть видимым.
- **Задача противоречит действующему правилу контракта** — не выбирай молча, чему следовать.
  Останови работу и покажи противоречие: «в контракте правило N говорит X, задача требует Y».
  Решение принимает человек, потому что контракт — это договорённость, а не деталь реализации.

**Каждое изменение контракта попадает в финальный отчёт отдельным списком** — что изменил,
какой случай это закрывает и какое поведение выбрано. Договорённость, которую человек не заметил,
ничем не лучше её отсутствия: контракт читает ещё и тот, кто пишет фронт.

Переиспользуй уже описанные DTO. Параллельная структура с тем же смыслом
(`BookingDto` рядом с `Booking`) — это будущий рассинхрон фронта и бэка.

## Шаг 2. Схема БД

Нужны ли эндпоинту новые поля, таблицы или индексы? Если да — правь `server/schema.sql`
до реализации.

Проверь, не покрыто ли требование существующими ограничениями: партиальный уникальный индекс
`bookings_active_slot_uniq`, `CHECK` на статусы и `weekday`, `REFERENCES` без `CASCADE`.
Часть правил контракта уже держится схемой — дублировать их проверками в коде не нужно,
достаточно корректно обработать ошибку БД (например, нарушение уникальности → `409`).

Живой базы в проекте сейчас нет: Postgres не установлен, `schema.sql` существует только файлом.
Значит запрос нельзя проверить исполнением — тесты идут на заглушках репозиториев и подтверждают
форму ответа, но не корректность SQL. Пиши SQL с этой оговоркой и называй её в отчёте.

Механизма миграций тоже нет. Когда база появится, правку `schema.sql` придётся сопровождать
ручным `ALTER TABLE ...` — поэтому уже сейчас выноси такое изменение в отчёт отдельным пунктом.

## Шаг 3. Реализация

Раскладка кода в `server/` — единая для всех эндпоинтов:

```
server/
├── app.js                 createApp({ ...repositories }) — CORS, json, роутеры, обработчик ошибок
├── index.js               точка входа: пул Postgres + listen
├── db.js                  создание пула
├── errors.js              HttpError и фабрики ошибок контракта
├── routes/                разбор HTTP: параметры, валидация тела, коды ответов
├── services/              правила предметной области: пересечение интервалов, переходы статусов
├── repositories/          SQL и только SQL
└── mappers/               snake_case из БД ↔ camelCase DTO контракта
```

Слой `services` остаётся, даже если у конкретного эндпоинта «нет логики»: как только правило
появится, его место уже определено, и не придётся переносить код между слоями задним числом.
Единообразие здесь важнее экономии одного файла — эндпоинтов в контракте четырнадцать.

`createApp` принимает репозитории аргументом. Это не церемония, а то, что позволяет тестам
работать без поднятого Postgres.

Что важно независимо от слоёв:

- **camelCase в API, snake_case в БД.** Контракт отдаёт `eventTypeId`, `startTime`,
  `durationMinutes`; таблицы хранят `event_type_id`, `start_time`, `duration_minutes`.
  Преобразование живёт только в `mappers/` — разъехавшийся маппинг даёт молчаливые `undefined`
  в ответе вместо ошибки.
- **Занятость слота — пересечение интервалов**, а не совпадение времени начала:
  активная бронь `[S, S+durB)` пересекает искомый `[T, T+dur)`. Генерация свободных слотов
  и валидация при создании брони обязаны использовать **одну** функцию пересечения —
  две независимые реализации разъезжаются на первой же правке длительности.
- **Ошибки** — в формате `{ error: "machine_code", message: "русское описание" }`.
  `error` читает фронт, `message` читает человек.
- **Таймзона** берётся из `AvailabilitySchedule.timezone` того расписания, к которому
  привязан тип события. Сервер не использует свою локальную зону и не принимает offset от клиента.
- **Числовые пределы и прочие константы** (максимальная длина поля, лимиты) не дублируй
  в схеме и в коде двумя независимыми значениями. Держи одно место — либо ограничение в БД,
  либо константу в коде. Если по делу нужны оба, назови это в отчёте: «лимит N задан в двух
  местах, при изменении править оба».

## Шаг 4. Тесты

Инструменты: **Vitest + supertest**.

Для каждого эндпоинта пишутся три группы:

1. **Happy path** — успешный сценарий с проверкой формы ответа: коды, все поля DTO из контракта.
2. **Ошибки** — каждый код ответа, указанный в контракте для этого эндпоинта (`400`, `404`,
   `409`), с проверкой значения `error`, а не только статуса.
3. **Граничные случаи** — там, где логика опирается на интервалы и статусы: слот впритык
   к концу рабочего окна, соседние непересекающиеся слоты, бронь в статусе `cancelled`
   (слот снова свободен), повторная запись на занятый слот.

Тест на «форму ответа» стоит писать против контракта, а не против текущего кода: если код
отдаёт лишнее поле, тест должен это поймать, иначе фронт получит то, чего не ждёт.

**Мапперы тестируй отдельным файлом**, а не только через HTTP. Через эндпоинт видно лишь то,
что попало в ответ; отдельный тест ловит рассинхрон DTO прямо: публичный Booking не содержит
`adminNote`, админский не содержит `token`, `date` из Postgres приходит объектом `Date`
и должен отдаваться строкой `YYYY-MM-DD` без сдвига на сутки.

## Шаг 5. Самопроверка перед отчётом

Прежде чем сказать «готово», проверь по списку — и допиши недостающее, а не упомяни в отчёте:

- [ ] Контракт и код описывают одно и то же: путь, метод, коды ответов, состав DTO.
- [ ] Все коды ответов из контракта реально возвращаются кодом и покрыты тестами.
- [ ] Ни в одном админском ответе о брони нет поля `token`.
- [ ] На публичных `bookings`-эндпоинтах несуществующий `id` и неверный `token` дают
      **одинаковый** `404 booking_not_found`.
- [ ] Изменения контракта вынесены в отчёт отдельным списком (Шаг 1).
- [ ] Правка `schema.sql` сопровождается готовым `ALTER TABLE` (Шаг 2).
- [ ] Тесты прогнаны, зелёные, и `git diff` не содержит правок в тестовых файлах,
      сделанных ради того, чтобы тест позеленел.
- [ ] `npm run lint` зелёный. Правило линтера не отключается ради своего кода: если оно мешает,
      это повод назвать его человеку, а не дописать `eslint-disable`.

**Если тесты прогнать нельзя** (нет установленных зависимостей, нет базы) — не считай пункт
выполненным и не пиши «готово» без оговорки. Скажи прямо: тесты написаны, но не запускались,
причина такая-то, проверено тем-то (например, `node --check`). Невыполненный шаг, названный
вслух, стоит дёшево; невыполненный шаг, поданный как выполненный, стоит отладки на проде.

Пункт про `git diff` важен по той же причине: зелёный прогон означает «критерий выполнен»,
а не «поведение правильное». Подогнать тест под код — самый простой способ получить зелёный
прогон и самый дорогой в отладке потом.

## Правила контракта, которые легко потерять

Собраны здесь, потому что все они «невидимы» в коде отдельного обработчика и всплывают
только при чтении контракта целиком:

| Правило | Почему так |
|---|---|
| Единый `404 booking_not_found` на неверный `id` **и** неверный `token` | Анти-оракул: разные ответы позволяют перебором `id` узнать, какие брони существуют |
| `token` не отдаётся в админских ответах | Админу он не нужен; секрет не размножается по ответам без необходимости |
| Отмена — мягкая (`status='cancelled'`) | Слот освобождается, история сохраняется |
| `DELETE` типа события / расписания при связанных записях → `409` | Запрещено на уровне БД (`REFERENCES` без `CASCADE`); скрывать нужно через `PATCH hidden: true` |
| Публичные эндпоинты — по `slug` и с фильтром `hidden: false` | `hidden` — это фильтр публичности; админ по `id` видит всё |
| `completed` и `pending → confirmed` — только вручную | Шедулера в проекте нет осознанно |
| Бэк и фронт на разных origin | Нужен явный CORS, иначе рабочий эндпоинт не доедет до SPA |

Анти-оракул надёжнее держать структурой, а не дисциплиной: если искать бронь одним запросом
`WHERE id = $1 AND token = $2`, то «нет такого id» и «token не тот» становятся физически
неотличимы — одна ветка, один ответ, одинаковое время выполнения. Тогда разойтись они не могут
даже при последующих правках.

## Эталон

Публичные типы событий — первый реализованный эндпоинт, сделан по этой процедуре.
Читай эти файлы как образец, прежде чем писать свои: следовать готовому примеру надёжнее,
чем восстанавливать конвенцию по описанию.

| Слой | Файл |
|---|---|
| Роут | `server/routes/public/event-types.routes.js` |
| Сервис | `server/services/event-types.service.js` |
| Репозиторий | `server/repositories/event-types.repository.js` |
| Маппер | `server/mappers/event-type.mapper.js` |
| Сборка приложения | `server/app.js` |
| Тест эндпоинта | `server/tests/public-event-types.test.js` |
| Тест маппера | `server/tests/event-type.mapper.test.js` |
| Заглушка репозитория | `server/tests/helpers/fake-event-types-repository.js` |

На что смотреть в эталоне:

- Заглушка репозитория повторяет **семантику SQL**, а не удобную для теста логику: фильтр
  `hidden = false` применяется при выборке. Если заглушка фильтрует иначе, чем запрос,
  тесты проверяют не то поведение, которое поедет в прод.
- Состав полей в тесте сверяется со списком из контракта целиком, а не по одному полю —
  так ловится не только пропавшее поле, но и лишнее.
- Приём анти-оракула перенесён на типы событий: скрытый `slug` отвечает ровно тем же,
  чем несуществующий.
