# AGENTS.md

Запись на события (Calendly-подобный сервис, «Календарь звонков»). Клиент выбирает тип события, дату и свободный слот; владелец управляет типами событий, расписаниями доступности и статусами броней через отдельное SPA.

Контракт API — `API-CONTRACT.md` (источник истины для фронта и бэка). Статус проекта и план этапов — `PLAN.md`.

## Команды

- `npm install` — зависимости (Express 5, pg, cors; Vitest и supertest — dev)
- `npm start` — сервер на `PORT` (по умолчанию 3000), нужен `DATABASE_URL`
- `npm test` — тесты (Vitest); БД не требуется, репозитории подменяются заглушкой
- `npm run lint` — ESLint (flat config, `eslint.config.js`); должен быть зелёным перед словом «готово»
- `npm run db:init` — накатить `server/schema.sql` через `psql "$DATABASE_URL"`

**Базы данных сейчас нет.** Postgres в системе не установлен, `psql` недоступен, `DATABASE_URL` не задан — `npm run db:init` и `npm start` выполнить нельзя. Проверять свою работу можно только через `npm test` и `npm run lint`: тесты идут на заглушках репозиториев, поэтому не подтверждают, что SQL-запрос корректен. Ошибки в SQL всплывут при первом реальном подключении.

Механизма миграций нет. Когда база появится, правка `schema.sql` на уже накатанной базе потребует ручного `ALTER TABLE`.

Фронт (`ui/`) ещё не начат.

## Стек

- Бэк: Node + Express — `server/`
- БД: PostgreSQL, схема — `server/schema.sql`
- Фронт: Vue (SPA) — `ui/`, отдельный процесс и деплой от бэка

## Структура

- `server/` — Express-приложение, `schema.sql` (модель данных). Раскладка: `routes/` (HTTP) → `services/` (правила) → `repositories/` (SQL), плюс `mappers/` (snake_case ↔ camelCase) и `errors.js`. `createApp` принимает репозитории аргументом — поэтому тесты идут без Postgres
- `.claude/skills/` — скиллы проекта, поднимаются сами по своему `description`: `new-endpoint` (процедура добавления и правки эндпоинта), `db-layer` (устройство слоя данных)
- `ui/` — Vue SPA (публичная запись + админка)
- `API-CONTRACT.md` — DTO, эндпоинты, ключевые правила
- `PLAN.md` — статус этапов, принятые решения

## Конвенции

- Все конвенции API (JSON, `{error, message}`, формат дат/времени, статусы брони, токен вместо email, поведение `DELETE`) — см. `API-CONTRACT.md`, здесь не дублируются
- Перед реализацией нового DTO/эндпоинта — сверяться с `API-CONTRACT.md` и переиспользовать уже описанные там типы; не создавать параллельные структуры данных без явной необходимости
- Слот занят, если активная бронь `[S, S+durB)` пересекает `[T, T+dur)` — пересечение интервалов, а не точка
- Защита от гонки на пересекающихся слотах — партиальный уникальный индекс `bookings_active_slot_uniq` (`event_type_id, date, start_time`) в Postgres (`server/schema.sql`). В отличие от барбершопа, здесь защита не зависит от однопоточности Node: уникальность гарантирует сама СУБД, даже при нескольких процессах/инстансах бэка
- Часовой пояс — в `AvailabilitySchedule.timezone` (IANA), не на сервере; арифметика слотов ведётся в этой таймзоне, клиент offset не передаёт
- Бэк и фронт — разные origin (раздельный деплой), на сервере нужен явный CORS
- UI — на русском
