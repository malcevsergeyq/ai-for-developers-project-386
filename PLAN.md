# План и статус проекта

Онлайн-запись на события (Calendly-подобный сервис, вариант «Календарь звонков»). Владелец создаёт типы событий, каждый привязан к расписанию доступности; клиент выбирает тип события, дату и свободный слот и записывается. Раздельные фронт и бэк (по требованию задания): бэк — API ниже, фронт — SPA (Vue).

## Стек

- Бэк: Node + Express — `server/`
- БД: PostgreSQL — учебный выбор: практика с клиент-серверной БД и раздельным деплоем фронта/бэка (не продиктовано сложностью модели данных как таковой — с ней справился бы и `node:sqlite`, как в барбершопе)
- Фронт: Vue (SPA) — `ui/`

## Ключевые решения (Design First, до кода)

- Два контура: публичный (запись клиентов, без авторизации, адресация по `slug`) и админский (`/admin/*`, по `id`, авторизация вне скоупа контракта)
- Слот — интервал `[startTime, startTime+durationMinutes)`; занятость — пересечение интервалов, как в барбершопе: `[S, S+durB)` и `[T, T+dur)`
- Уникальность `(eventTypeId, date, startTime)` + `status IN ('pending','confirmed')` на уровне БД, гонка → `409`; генерация слотов и валидация `POST` — через одну функцию пересечения
- В отличие от барбершопа, `endTime` хранится и возвращается явно, а не только `startTime`
- Таймзона живёт в `AvailabilitySchedule.timezone` (IANA), а не на сервере — `weekday` и слоты считаются в ней, клиент не передаёт offset
- Отмена — мягкая (`status='cancelled'`), слот снова свободен
- `hidden` — только фильтр публичности; админ видит все типы событий
- **Доступ клиента к своей брони (просмотр/отмена)** — не email, а непрозрачный `token` (случайная строка), выдаётся один раз в ответе на создание брони; используется единообразно и для чтения (`GET`), и для отмены (`POST .../cancel`) — email как секрет для сверки не используется
- Несуществующий `id` и неверный `token` на публичных `bookings`-эндпоинтах → **одинаковый** `404 booking_not_found` (анти-оракул: не даёт перебором `id` узнать, какие записи вообще существуют)
- `token` возвращается клиенту только в ответе на создание и в ответе на `GET .../bookings/:id`; в админских списках/карточках брони поле `token` не отдаётся (не нужно админу, минимизация распространения секрета) — *решение агента по умолчанию, поправь если нужно иначе*
- `completed` — выставляется вручную админом, без шедулера (не оправдано для масштаба проекта)
- `pending → confirmed` — тоже вручную владельцем через `PATCH /admin/bookings/:id/status`; `pending` осознанно оставлен как отдельный статус — ручное одобрение заявок на встречу
- `/admin` — отдельное SPA на Vue поверх этого API (не серверный рендеринг, как в барбершопе) — больше типов сущностей и настроек, чем одна форма записи, плюс задание требует раздельные фронт и бэк

## Ключевые решения — модель данных

- `schedule_rules` — отдельная таблица (не `jsonb`-массив внутри `availability_schedules`): обычные индексы/сравнения по `start_time`/`weekday`, плюс практика с реляционной моделью
- Удаление `event_types`/`availability_schedules` при наличии связанных записей (броней / типов события) — запрещено на уровне БД (обычный `REFERENCES` без `CASCADE` → Postgres отклонит, API отвечает `409`); для скрытия — `hidden: true`, не `DELETE`
- Партиальный уникальный индекс `bookings_active_slot_uniq (event_type_id, date, start_time) WHERE status IN ('pending','confirmed')` — аналог `(date, start_time) WHERE status='active'` из барбершопа, расширен на `event_type_id` и два активных статуса

## Открытые вопросы

- **`token` в query-string** у `GET /api/public/bookings/:id` попадает в access-логи прокси и в историю — тот же класс риска, из-за которого отказались от email в query. Возможная замена — заголовок; это правка контракта, решение не принято.
- **Миграций нет.** Заводить каталог миграций или нет — не решено. Пока база не накатана, вопрос не горит: до первого `db:init` схема правится свободно. Накопленные правки схемы после 2026-08-03, если база всё-таки окажется накатанной: `CREATE INDEX schedule_rules_schedule_id_idx ON schedule_rules (availability_schedule_id);`
- **Postgres не поднят** (обнаружено 2026-08-09 при аудите агентной системы). Пока его нет, ни один SQL-запрос в репозиториях не исполнялся ни разу — тесты идут на заглушках и корректность SQL не подтверждают. Решить, где поднимать: локальная установка или Docker (последнее заодно готовит требование задания про Docker-образ).
- **`/api/admin/*` ничем не защищён** — авторизация вынесена контрактом за скоуп.
